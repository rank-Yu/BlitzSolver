# 用药调度三组离线对照

本实验比较普通无强制指令请求的三种尾部调度：`one-allowed` 为最多 1 次、然后按原请求放开；`one-two-three` 为最多 1、2、3 次，是当前生产默认；`one-two-allowed` 为最多 1、2 次、然后按原请求放开。每层均从同一原根开始；主组合、策略、宽度、总预算和内存设置相同。实验只扩展 `tests/Differential` 的离线选项，没有改 Core、Mod 或生产默认。

## 实验方法与合同

三组按上述顺序运行同一份冻结二进制，使用同一 120 根质量语料、中档、4 进程、120,000 ms 总预算及 2,576,980,377 字节逻辑内存预算，保留既有 64 位状态池预算修复。冻结 Differential.dll SHA-256 为 `a37eb74699bc98c7175eccbffe52c018cc3eb04fd069216c293c10d7290fc5c2`，Core.dll 为 `f948ba320b1cc34420bd88d54ee0ada62a4a304542532e44c944704682e32ba4`。命令中的 `MODE` 依次为上面三种名称：

```bash
dotnet .local/potion-schedule-trial/frozen-bin/Differential.dll \
  --offline-combat --corpora tests/corpora --jobs 4 --search-tier Medium \
  --potion-schedule "$MODE" --out ".local/potion-schedule-trial/$MODE"
```

每组的 120 个请求原始 `MaximumUses` 均为不限次，初始和最低用药次数均为 0，均无强制指令；因此这批样本中自定义成员不会因原上限产生重复有效层。强制指令仍使用原 Allowed 主组合，未指定实验选项时保持现有搜索计划。显式 `one-two-three` 直接使用默认计划，保留它的有效上限去重；另两组通过 `CustomMembers` 复用同一无药主组合，不增加新的去重机制。父子进程显式传递选项，summary 标明计划，逐根附带原始次数约束；成员日志保留计划、有效上限、实际次数和采纳情况。

Solution、Differential Release 构建及 KernelChecks、Architecture、Golden K0 通过。合同验证三种成员的顺序、宽度、实际传给协调器的上限、强制计划和输入校验；真实父子进程的单根烟测确认三种成员日志顺序，非法值和非离线模式均被拒绝。Core 未修改，复用此前完整 D1/D2 的验证，不重复运行。

三批结束后，实验 helper 从“移除默认尾部三个成员”改为“筛选无药主成员”，以免未来默认尾部变化时误删主成员。对本次默认计划，两种写法产生相同成员，相关计划合同重新通过；没有重跑质量批次。测量版本 helper 的 SHA-256 为 `dd48278b018a48e9bcb1404f9e605abcbc700a9be668990b72646504c637bcbf`，最终 helper 为 `3bde3f053eda31e3bb8599797adfba6ba5588e04671711d78fbfa1f112b77139`；其余实验源码哈希和冻结二进制哈希保存在证据中。

## 三次以上用药的可观察范围

两种含 Allowed 的组，各有 64 个 Allowed 成员运行，其中各有 2 个成员的按次数候选摘要不完整。其余完整摘要各记录到相同三个实际累计 4 次的候选：NECROBINDER-008、DEFECT-016、NECROBINDER-017；三个均为败局、不符合政策资格，未被最终采纳。每组这些候选的 `PotionCandidatesComplete` 均为 true。`one-two-three` 的 Two 和 Three 层也各有 2 个摘要不完整；层上限本身限制主动用药至 2 或 3 次。

这些摘要是实际访问或保留过的各次数最佳候选，不是穷举。摘要不完整的成员可能遗漏候选，因此只能说本次可观察到的三条四药候选没有形成可采纳获胜结果，不能证明其他候选没有被搜索或放开策略没有潜在收益。
